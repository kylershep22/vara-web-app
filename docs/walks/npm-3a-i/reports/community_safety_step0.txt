HEADLINE FINDINGS
S1. Admin removals and auto-hides do nothing on mobile. Both the auto-moderation trigger and an admin "remove" set posts/{id}.hidden = true (functions/src/admin/moderation.js:214, 245, 286; moderationActions.js:112-115, 129-132). The mobile feed and group feed never read `hidden`. They filter only on deleted, per-user hiddenPosts and muted authors (mobile/src/hooks/useFeed.ts:161-169; useGroupDetail.ts:393-400). The rules do not block reads of hidden posts either (firestore.rules:348-358).
S2. Any signed-in user can rewrite any post's comments and likes. The posts update rule lets ANY authenticated, active user change the keys likes/comments/likesCount/commentsCount/updatedAt on any post (firestore.rules:377-380). Comments are an array inside the post (community.service.ts:418-430). Anyone can therefore delete other people's comments, forge comments under another user's userId and authorName, and inflate likes.
S3. Image moderation never runs on mobile posts. onPostCreate_moderateContent checks post.imageUrl (moderation.js:225). Mobile writes media[] and images[] and never imageUrl (community.service.ts:303-304). Comments, edits, DMs, profiles, group and challenge text, and avatars are never moderated at all. The keyword blocklist reads config/moderationBlocklist, and Kyle reported on 2026-10-01 that no config collection exists (roadmap line 2548). If that still holds, the blocklist is empty.
S4. Kyle would not find out about a report. A report writes postReports. If the admin functions are deployed, a trigger copies it into moderationQueue (moderation.js:320-371). Nothing alerts anyone: no email, no push, no log-based alert. The only viewer is the web admin dashboard, and the production web build is gated off.
S5. The repo's Terms promise blocking, and the app has none. mobile/TERMS_OF_SERVICE.md:111-113 says "Connection requests can be accepted, declined, or blocked" and "Blocked users cannot contact you or see your profile". There is no blocking anywhere in the code. The published web Terms (the URL the app links to) differ: they say 16+, contain no blocking promise, and give support@varawellness.co. The repo copy says 13+ (16 in Europe) and support@varawellness.com (line 311).
S6. Suspension is partial. isActiveUser() gates creating posts, groups, challenges, conversations and messages, but not connection requests (rules:627-635), invites, comments-by-update... (see item 2). A suspended user is never told; their writes simply fail.
S7. Accepted connections are permanent in the mobile app. There is no remove-connection or disconnect action anywhere in mobile/src. The rules allow delete (firestore.rules:647-653), but nothing calls it. A helper for a deterministic connection ID exists, getConnectionId (community.service.ts:450), but nothing uses it.

3. BLOCK USER
======================================================================
Confirmed: no blocking exists. firestore.rules has no blocks collection (match list: lines 61-1348). mobile/src has no block service or UI; the "block" hits are time-blocking. No server code exists either. The only mention is the repo Terms promise (S5).

Where a block must be enforced, and where it can be enforced:
  - Feed (posts by the other user): APP ONLY. A per-document block check in the posts read rule would make every feed query fail, because rules are not filters. Extend the existing mute filter (useFeed.ts:161-169, useGroupDetail.ts:393-400), applied in both directions.
  - Comments inside posts: APP ONLY (CommentModal filter).
  - Profile viewing (users/{uid}): RULES are possible for single-document get only, by splitting get and list on users. But users docs are read for author names everywhere, so a rule denial would break rendering of shared group content. Recommend APP: UserProfileScreen shows an unavailable state.
  - Discover, People, search and suggestions: APP ONLY (list queries). connections.service.ts suggestions and searchUsers (community.service.ts:790).
  - Creating a connection request: RULES. After NPM-3a pins requesterId/addresseeId: !exists(block A->B) && !exists(B->A). Blocking should also remove or decline any pending or accepted connection between the two (client or server).
  - Creating a conversation: RULES. After NPM-3a's exactly-two-participants rule: block exists() checks on participants[0] and [1].
  - Writing a message: RULES. After NPM-3a binds receiverId: block exists() checks on senderId/receiverId. That is two exists() calls added to the existing conversation get(). The 10-lookup limit allows it.
  - Existing conversation: the same message rule stops new messages. Reading history is a product choice (CS-D3). The APP hides the conversation from the blocker's list.
  - Community push sender (functions-notifications, after NPM-3a): SERVER. Read both block docs before sending. This is defence in depth, since the rules would already stop the write.
  - Group membership and shared groups: APP ONLY (filter content). Joining a group the other user is in cannot sensibly be blocked.
  - Invites (group and challenge): RULES are possible on create (exists checks on inviter and invitee).
Data-model options (Kyle rules):
  BK1 (recommended): users/{blockerUid}/blockedUsers/{blockedUid} {createdAt}, owner-only read and write.
    - Rules check exists(/databases/$(database)/documents/users/$(a)/blockedUsers/$(b)) in both directions.
    - Rules can read documents regardless of read rules, so the blocked user cannot see that they are blocked.
    - Deleted automatically with the blocker's users/{uid} recursive delete (accountDeletion.js:180-187).
    - A blocked list in Settings is a simple owner query.
  BK2: top-level blocks/{blocker}_{blocked} {blockerId, blockedId}. The same deterministic exists() checks. Needs a new manifest entry (OWNER_FIELD_COLLECTIONS blockerId) and a new rule block. Mirrors mutedUsers' shape.
  BK3: an array on userPrivate/{uid}.blockedUids. Rules can get() it, but array size limits apply and one doc is contended. Not recommended.
  BK4: fold into mutedUsers with a level field. It mixes a soft feed preference with a safety boundary. Not recommended.
Recommended enforcement: rules for connection, conversation, message and invite creation; server check in the push sender; app filters for feed, comments, people, search, profile and the conversation list; blocking also removes the connection.

5. THE NON-CONNECTION MESSAGE-WRITE GAP
======================================================================
Today: the conversation create rule (firestore.rules:664) and the message create rule (:682-684) never refer to connections. The UI gates starting a conversation on an accepted connection (Addendum 1 A4), but a direct SDK call does not. Connection docs have auto IDs (community.service.ts:522), and a deterministic-ID helper exists but is unused (:450). Mobile has no way to disconnect (S7). Accepted connections can only end through account deletion or a direct SDK delete.
Options:
  G1: a deterministic connection ID, connections/{sortedA}_{sortedB}. Rules then use get() directly.
      Cost: migrate every existing auto-ID connection (an admin script with a re-key); change every writer and reader (mobile community.service.ts, connections.service.ts, useConnections; web, which is dormant); handle the historical shapes (a/b, requesterId, participants). The rules also need the create to use that ID. This is the largest change and touches a lot of tested code.
  G2: a server-maintained index, connectionIndex/{sortedA_sortedB} {status}, written by an onDocumentWritten trigger on connections. Rules check that the index exists with status 'accepted'.
      Cost: one new function and its deploy, a one-time backfill script, and eventual consistency: messaging right after accepting may fail for about a second. The client is unchanged. Rules depend on a function being deployed and healthy.
  G3 (recommended): the conversation carries connectionId.
      - Conversation create requires get(connections/$(connectionId)) to have status 'accepted', and its participants array to contain both conversation participants.
      - Message create gets the conversation (it already does), then the connection, and requires it to still be accepted.
      Cost: createOrGetConversation (messaging.service.ts:61-100) must look up and pass the connection ID. useConnections already holds the connection docs. Existing conversations have no connectionId, so they need a backfill (an admin script matching on participants) or they become read-only. Rules lookups per message are conversation + connection + 2 block checks = 4. No new function.
      It is synchronous and fully rule-enforced, and later disconnect or block works naturally.
  G4: move conversation and message creation behind a callable with server checks. The largest rewrite, adds latency, and breaks the client's offline queueing. Not recommended.
  G5: status quo (app-only gate). It does not close the gap.
After disconnect (a product decision; disconnect does not exist today, S7):
  - (a) the conversation becomes read-only for both. Recommended; it follows naturally from G3.
  - (b) the conversation is hidden for both.
  - (c) messaging continues as before.
  If a disconnect action is added, it should be the same action as, or adjacent to, Block (CS-D4).

6. ABUSE AND RATE LIMITS
======================================================================
Today: nothing limits DMs, conversations, connection requests, posts, comments, reports or invites (Addendum 1 A4). The existing rateLimit covers the AI endpoints only.
Options:
  RL1, rules-only minimum interval. Batch each create with an update to a per-user rate doc, for example userPrivate/{uid}.lastMessageAt or a dedicated rateWrites/{uid}. Rules use getAfter()/get() to require request.time >= previous + N seconds, and require the rate doc to be updated in the same batch.
    - Enforceable WITHOUT a server function.
    - Per-window counters (for example ≤ 50 per hour) are possible with count and windowStart fields, at the cost of complex rules.
    - Cost: every writer becomes a batch, and the rules get more complex.
  RL2, a server trigger with auto-suspend. Writes stay client-side. onDocumentCreated on directMessages, connections and posts increments a per-user counter. Past a threshold it sets moderationStatus 'suspended' for a short window and queues a 'rate_limit' item.
    - Needs a function, but writes are not moved behind it.
    - Enforcement is through isActiveUser, so isActiveUser must be added to connections create (and the others in 2c).
    - Reactive: the threshold-crossing burst lands.
  RL3: move the writes behind a callable using checkRateLimit. The heaviest option; not recommended.
  RL4: Firebase App Check. It stops scripted non-app clients but is not a per-user limit. A complement at most.
Recommendation:
  - RL1 for connection requests (low volume; a minimum interval and a per-day cap).
  - RL2 for messages and posts, with conservative thresholds.
  - Add isActiveUser to connections, invites and conversation update.
  - Both RL1 and RL1-style caps are enforceable without moving writes behind a function. RL2 needs a function but keeps writes client-side.
