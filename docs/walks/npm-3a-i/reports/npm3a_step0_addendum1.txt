Rule for creating a conversation (firestore.rules:658-671, in full):
    // Conversations
    match /conversations/{conversationId} {
      // Read: if document doesn't exist (checking before create) OR user is a participant
      allow read: if isAuthenticated() && (resource == null || request.auth.uid in resource.data.participants);

      // Create: if user is one of the participants
      allow create: if isAuthenticated() && isActiveUser() && request.auth.uid in request.resource.data.participants;

      // Update: if user is a participant (for lastMessage update)
      allow update: if isAuthenticated() && request.auth.uid in resource.data.participants;

      // Delete: not allowed (use Cloud Function if needed)
      allow delete: if false;
    }
Rule for creating a directMessages document (firestore.rules:673-688, in full):
    // Direct Messages
    match /directMessages/{messageId} {
      // Read: if user is a participant in the conversation
      allow read: if isAuthenticated() && (
        resource == null ||
        request.auth.uid in get(/databases/$(database)/documents/conversations/$(resource.data.conversationId)).data.participants
      );

      // Create: if user is the sender AND a participant in the conversation
      allow create: if isAuthenticated() && isActiveUser() &&
        request.auth.uid == request.resource.data.senderId &&
        request.auth.uid in get(/databases/$(database)/documents/conversations/$(request.resource.data.conversationId)).data.participants;

      // Update/Delete: messages are immutable
      allow update, delete: if false;
    }

What unregisterForNotificationsAsync does on iOS in this version:

  Native (ios/EXNotifications/PushToken/PushTokenModule.swift:44-47):

  It does exactly one thing: UIApplication.shared.unregisterForRemoteNotifications(). It does not clear the Expo server registration flag (see below), does not notify Expo's servers, and does not touch any token stored in Firestore.

Does it affect locally scheduled notifications?
  - The package source does not touch them. Local scheduling in this package goes through the UNUserNotificationCenter-based scheduler modules, which are separate from PushTokenModule, and unregisterForRemoteNotifications is a UIApplication remote-notification (APNs) API.
  - The package source does NOT settle iOS's runtime behaviour. Apple's API concerns APNs registration, not the local notification center or the user's authorization, but this was not verified from the package or on a device.
  - Verifying it is a device check: schedule a local notification, call the API, and confirm it still fires.

Does getExpoPushTokenAsync register the device again on the next call?
  Yes, by source:
  - getExpoPushTokenAsync (build/getExpoPushTokenAsync.js:45-46) calls getDevicePushTokenAsync() unless a devicePushToken is passed in.
  - That calls the native getDevicePushTokenAsync (PushTokenModule.swift:25-41), which calls UIApplication.shared.registerForRemoteNotifications() (line 40) and resolves on didRegister (lines 50-53).
  - The app's own T1 path (registerAndSaveFCMToken, which calls getDevicePushTokenAsync at mobile/src/services/notifications.service.ts:369) also re-registers on every sign-in.

  IMPORTANT, from source: re-registration also happens automatically at every app launch (N2).
  - getExpoPushTokenAsync calls setAutoServerRegistrationEnabledAsync(true) after a successful fetch (getExpoPushTokenAsync.js:92-98). That persists registration info {isEnabled:true} natively (DevicePushTokenAutoRegistration.fx.js:21-29).
  - At module load, DevicePushTokenAutoRegistration.fx.js:57-85 reads that persisted info. If it is enabled, it calls getDevicePushTokenAsync() (line 50), and that native call registers for remote notifications. It then uploads the token to Expo's server (line 51).
  - It also installs a global addPushTokenListener that is never cleared (lines 60-80).
  - The fx module is loaded whenever expo-notifications is imported, because build/index.js:35 re-exports from it.
  - Consequence: an app that ever called getExpoPushTokenAsync (this one does) re-registers with APNs on the next cold launch, signed in or not, undoing an unregister done at sign-out.
  - Keeping a signed-out device unregistered across launches would also require setAutoServerRegistrationEnabledAsync(false) (exported at build/index.js:35; it clears the persisted info at line 28).

Is the Expo token the same or different afterwards? The package source does NOT settle this.
  - The token string is minted by Expo's server (POST https://exp.host/--/api/v2/push/getExpoPushToken, getExpoPushTokenAsync.js:7, 62-79) and returned as data.expoPushToken (:121-131). The package only relays it.
  - The request body is {type:'apns', deviceId, development, appId, deviceToken, projectId} (:63-70).
  - deviceId is an installation ID kept in the iOS Keychain (ios/EXNotifications/ServerRegistration/ServerRegistrationModule.swift:26-46), with accessibility kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly (:82). It is stable across an unregister and re-register.
  - Whether Expo's server returns the same token for the same deviceId/projectId, and whether APNs issues the same device token after unregister and re-register, are both outside this package. Neither is settled here.
  - Relevant to the dev-client vs standalone question: `development` comes from Application.getIosPushNotificationServiceEnvironmentAsync() (:151-164), so the dev client and a production build send different `development` values, and the dev client's APNs token is a sandbox token.
