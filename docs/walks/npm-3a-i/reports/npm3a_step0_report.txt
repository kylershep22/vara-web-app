HEADLINE FINDINGS
H1. On an iPhone, only one of the two DM senders can deliver. functions-notifications/notifyOnDirectMessageCreated sends through the Expo push service to userPrivate.expoPushToken. functions/onNewDirectMessage sends through FCM (admin.messaging) to userPrivate.fcmToken. On iOS that field holds a raw APNs device token, because the app has no Firebase Messaging native SDK. FCM rejects a raw APNs token, so that path cannot deliver on iOS. This is derived from the code plus the libraries' documented behaviour and has NOT been checked on a device. Item 12 gives a read-only console check that settles it.
H2. The only path that delivers on iOS ignores every preference. Direct Messages OFF, General OFF and Quiet Hours do nothing on an iPhone today.
H3. Most new users never get an Expo token saved. Onboarding fetches the token and throws it away. The token is saved only when the user opens Settings (useNotifications on mount) or grants through NPM-2's permission row. A user who grants permission during onboarding and never opens Settings receives no DM pushes on iPhone.
H4. Connection requests produce no push for anyone. The app writes requesterId/addresseeId. onNewConnection reads a/b and returns early. notifyOnInviteCreated listens on connectionInvites, which only the dormant web app writes, and it sends no push in any case.
H5. Security: any signed-in, non-suspended user can push arbitrary text to any user. The directMessages create rule never checks receiverId, and the conversations create rule lets a user open a conversation with any uid. The push body is "<sender displayName>: <text>", and displayName is user-controlled. The connections create rule lets a user write a: <anyone>, b: <victim> with themselves as requesterId, so once onNewConnection reads the right fields it can send a request that appears to come from a third person. There is no blocking model anywhere.
H6. Nothing removes a token at sign-out, forced sign-out or account switch. A signed-out or switched iPhone keeps receiving the previous account's DM pushes, including message text, on the lock screen. Only account deletion removes the tokens, and it does so on the server.

Tokens the phone stores, and what each is on iOS:
  - expoPushToken: Notifications.getExpoPushTokenAsync({projectId:'63c2515a-...'}) (mobile/src/services/notifications.service.ts:123). On iOS it returns an Expo push token ("ExponentPushToken[...]"). Expo's service delivers it to APNs using the APNs key held in EAS credentials. Sender B CAN deliver to an iPhone.
  - fcmToken: Notifications.getDevicePushTokenAsync() (notifications.service.ts:369). On iOS this returns the native APNs device token (a hex string). The app has no @react-native-firebase/messaging; package.json has only the "firebase" JS SDK and expo-notifications, so no FCM registration token is ever minted on iOS. The code comment at :368 ("returns the native FCM/APNs token") is accurate: FCM on Android, APNs on iOS. admin.messaging().send({token}) accepts only FCM registration tokens, so given an APNs hex string it fails with an invalid-argument or invalid-registration-token error. fcmSender.js:39-47 logs it and returns null. SENDER A CANNOT DELIVER ON iOS. (This is derived, not device-verified; see item 12, check P0.)

What an iPhone recipient receives today for one message (assuming both functions are deployed and running, per Kyle's state):
  - Both tokens stored: ONE push from Sender B ("New message" / "<name>: <text>"). Sender A's FCM send fails silently. Plus one bell doc.
  - Only expoPushToken: one push (B).
  - Only fcmToken: NO push. A fails and B finds no token. Bell doc only.
  - No token: no push. Bell doc only.
  Preferences change none of these outcomes on iOS, because B ignores them. (On Android, if any exist, both would deliver: two pushes per message, and the FCM one is subject to prefs and UTC Quiet Hours.)

Blocked or not connected: neither sender checks either one. No block model exists (no blocks collection in firestore.rules, nothing in mobile/src/services). Neither function reads connections. Neither the rule nor the senders require the two users to be connected.

How D1 and Community pushes coexist today: they do not conflict in code. Community senders ignore the flag, so the flag can stay OFF (missing) while Community pushes run. The conflict is latent. SOCIAL-PUSH-FLAG-BYPASS (roadmap line 373) frames the bypass as a defect.   O5-2: O5-1 plus a separate Community kill switch, for example config/notifications.communityPushEnabled, where a missing field or doc means ON so that nothing has to be created at launch. It allows an emergency stop without touching anything the scheduled senders read. It costs one more read per event and one more fact on Kyle's checklist.
  O5-3: gate Community on serverPushEnabled. Not recommended. Turning Community on would unlock all four scheduled senders whenever their schedules are running.
  Allowing Community without unlocking the scheduled senders: yes, under O5-1 or O5-2, because they share no flag.

  T2. useNotifications (mounted only by SettingsScreen.tsx:57). On mount, when user changes, and if granted, it calls registerForPushNotifications then savePushTokenToUser, writing userPrivate/{uid}.expoPushToken and pushTokenUpdatedAt.
  T3. useNotificationPermission.requestPermission (NPM-2's device-permission row), lines 92-101. After a grant from that row it calls registerPushToken then savePushTokenToUser. Best-effort, logged on failure.
  (Removed: NotificationOptInScreen, which is still registered at AppNavigator.tsx:1112 but no longer reachable per NPM-2.)
Storage:
  - userPrivate/{uid}: expoPushToken (single string) with pushTokenUpdatedAt, and fcmToken (single string) with fcmTokenUpdatedAt. setUserPrivate merges.
  - Legacy fallback read by both codebases: users/{uid}.expoPushToken and users/{uid}.fcmToken, from old builds. Nothing writes them now.
  - One value per user, so there is no multi-device support: a second device overwrites the first.
  - The same device token CAN be present under two user documents at once. Nothing enforces uniqueness or clears the previous owner.
Gaps:
  - Grant during onboarding: OnboardingV3ReminderScreen.tsx:166 `void registerPushToken();` fetches the Expo token and DISCARDS it. Nothing is saved. T1 already ran at sign-in, before the grant, and returned null, so fcmToken is saved only at the next cold start. OnboardingAnchorScreen.tsx:137 and OnboardingV2ProtocolScreen.tsx:64 (older arcs) also grant without saving.
  - Grant from the routine editor (RoutineEditor.tsx:340), and the focus timer's ensureNotificationPermission (notifications.service.ts:218): no token save.
  - Net effect: a user's Expo token, the only one that delivers on iOS, is saved only if they open Settings or use the Settings permission row (H3).
  - Token refresh: no Notifications.addPushTokenListener anywhere. A rotated APNs or Expo token is picked up only by the next T1 (FCM) or T2 run.
On sign-out, forced sign-out, account switch and deletion:
  - Sign-out (AuthContext.tsx:304-320 logout): signOut, then SecureStore.deleteItemAsync('userId'). NotificationContext's cleanup (NotificationContext.tsx:270-294) cancels LOCAL notifications and clears the intent journal. Tokens in Firestore are NOT touched.
  - Forced sign-out (AuthContext.tsx:147 on a failed token refresh; services/api/client.ts:83 on a 401 refresh failure): the same, with no token handling.
  - Account switch: A's userPrivate keeps the device token. When B signs in, T1 writes the same APNs token to B, and B writes the same Expo token if B reaches T2 or T3. The device then receives both A's and B's DM pushes.
  - Account deletion: the deleteAccount callable deletes userPrivate/{uid} and users/{uid} on the server (functions/src/lib/accountDeletion.js:26-27, 181), so both tokens and the legacy fallbacks are gone. It requires network to call at all.
  - So yes: a signed-out or switched iPhone still receives the previous account's DM pushes, with sender name and message text, from Sender B.
Does any cleanup depend on a write made at sign-out? There is no cleanup at sign-out at all, so nothing is lost offline today, because nothing is attempted. Any future cleanup that is a Firestore delete at sign-out would be lost if made offline and the app is then killed (memory-only cache). After sign-out, A's credentials are gone, so the owner-only userPrivate rule prevents a later replay by anyone else.
Purely local unregistration: none exists. No call to Notifications.unregisterForNotificationsAsync and no token listener.

9. TARGET DESIGN (options and recommendations; Kyle rules)
======================================================================
9a. One sender per event, and which codebase survives.
  S1 (recommended): the notifications codebase survives as the single Community sender. It already uses Expo and already delivers on iOS. Add preference reads (directMessages and connectionRequests only; no allNotificationsEnabled, no quietHours, no serverPushEnabled), the connections trigger with the right fields, and idempotency. Delete onNewDirectMessage and onNewConnection from the api codebase. Benefit: a Community deploy can be scoped to `--only functions:notifications`, which never touches the api codebase and its four paused schedules. Cost: this codebase has no test harness today; the build would add jest as a devDependency (an install during the build, not now) and refactor index.js into testable units.
  S2: the api codebase survives. Rewrite social.js to send through Expo (add expo-server-sdk to functions/) and delete the notifications codebase's two functions. Benefit: the existing jest and emulator harness and userFields helpers. Cost: every Community deploy is an api deploy, which re-deploys the four scheduled senders (item 10).
  S3: keep both and gate one off. Not recommended; it leaves the duplicate architecture the ruling says to resolve.
  For connections, notifyOnInviteCreated is retired either way (mobile never writes connectionInvites), or left as a dormant-web-only bell writer. That is decision K3.
9b. Token type.
  K-T1 (recommended): the Expo push token. It works on iOS today with EAS-managed APNs credentials, needs no native rebuild, and the sender library is already in use.
  K-T2: real FCM. Add @react-native-firebase/messaging and its config plugin, upload an APNs key to Firebase, and do a native rebuild. Heavy, and a new native dependency before launch.
  K-T3: direct APNs from the server using the raw device token. Needs APNs key handling in functions and an environment (sandbox or production) per token. Not recommended.
  Under K-T1, the fcmToken write (T1) becomes dead for Community. Whether to stop writing it, or leave it for NPM-3b, is decision K5.
9c. How the phone guarantees the token is registered.
  R1 (recommended): one ensurePushTokenRegistered(uid) owned by NotificationProvider. It runs on sign-in, on every foreground return when permission is granted (compare with a locally cached last-saved value, write only on change), and immediately after every grant path (onboarding V3, the routine editor, the Settings row, the focus timer). Plus Notifications.addPushTokenListener for rotation. useNotifications' token save goes away (its routing moves to NotificationContext, item 7).
  R2: patch each grant path individually. Simpler to reason about one at a time, but it repeats today's failure mode where one path is forgotten.
9d. One push per event.
  - A single trigger per collection (9a).
  - Idempotency: before sending, create notificationLog/{recipientUid}/community/{eventDocId} with .create(), which fails if it already exists. Skip on ALREADY_EXISTS. This is at-most-once: a crash between marker and send loses one push rather than duplicating it. Recommended. The alternative, marking after the send, is at-least-once and allows duplicates on retry.
  - Rules tighten so one user action makes exactly one valid doc: DM receiverId must be the conversation's other participant, and text must be a non-empty string under a size cap. Connection create as in item 3.
  - Also skip self-sends (receiverId == senderId) and suppress when the recipient is the sender's only participant.
9e. A token stops delivering after sign-out or account switch without relying on a write that can be lost offline.
  X1 (recommended, server-side, offline-proof for switching): single-owner tokens. On registration, the client also claims pushTokens/{sha256(token)} = {uid, updatedAt}. The sender delivers only if pushTokens/{hash(recipient's token)}.uid == recipientUid. When B signs in on A's phone, the claim moves to B and A's pushes stop, with no write from A needed. The rule allows the claimant to set uid only to their own. The risk is claiming someone else's token, which requires knowing a private token. It is acceptable and is documented.
  X2 (plain sign-out, offline): purely local Notifications.unregisterForNotificationsAsync() at sign-out, which stops remote delivery to the device until the next registration. MUST be device-verified first: that local notifications (the daily rhythm, routines, focus) keep working, and that the next sign-in's getExpoPushTokenAsync re-registers. Not verified in Step 0.
  X3: a best-effort online delete of userPrivate tokens at sign-out, done before signOut while the user is still authenticated. It helps when online but is not relied on.
  X4: client-side filtering of received pushes by recipient uid. Not viable on iOS for background pushes; the OS displays them without JS.
  Recommendation: X1 + X2 + X3, with X2 gated on a device check. If X2 fails that check, a signed-out-but-not-switched phone keeps receiving until the account signs in elsewhere or the token is invalidated. Record that as a known residual for Kyle.
