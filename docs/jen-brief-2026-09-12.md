## 2.3 The decisions that must be made before a string list can exist

In rough order of how much each one changes the list. Each is a genuine fork, not a
formality.

**D1 — What is this thing called on screen?** "Moments of joy" is the roadmap's
internal name. §8 bans "gratitude" outright but says nothing about whether "joy" is
itself user-facing. Every other string below inherits this answer. *Owner: Jen.*

**D2 — Does the below-fold row carry a label at all, or is it a bare control?** Row 8
says "one-tap entry sheet **from** D1 below-fold row". That is one surface or two
depending on the answer, and the D1 frame that would settle it is not in the repo.
*Owner: Kyle (structure), then Jen (the label, if there is one).*

**D3 — Does the sheet have a prompt line above the input, or only a placeholder in
it?** "Single-line input" describes the control, not whether it is framed by a
question. This is the difference between one string and two, and it is the most
voice-loaded string in the slice. *Owner: Jen.*

**D4 — Is there placeholder text in the input, and does it lead the user?** A
placeholder that suggests what counts as a moment is content; an empty field is a
decision to say nothing. *Owner: Jen.*

**D5 — What is the save affordance, and is there a dismiss label?** "One tap" (§1
`:36`, §8 `:657`) may mean the tap *is* the save, or may mean one tap to open. If
dismissal is gesture-only there is no cancel string; if there is a button, there is.
*Owner: Kyle.*

**D6 — Is there an acknowledgment after saving?** This is the sharpest constraint in
the slice. §8 `:657` says never counted; §8 `:661` says Vara "recognizes, never
grants permission"; the brand guidelines' §0.5 progress-and-celebration rule
(`docs/brand/Vara_Brand_Voice_Copy_Guidelines.md:69`) governs anything congratulatory.
A silent close is a legitimate answer and may be the right one. *Owner: Jen.*

**D7 — Can the user log more than one moment a day, and does the row change once
they have?** "No list surface on Today" rules out a list; it says nothing about the
row's own state after the first entry. If the row has a second state, that is another
string. *Owner: Kyle (behaviour), Jen (the second-state string if it exists).*

**D8 — Is there a character limit, and is a counter shown?** There is no app-wide
convention to inherit: existing `maxLength` values run from 8
(`EventCodeSheet.tsx:126`) to 500 (`AIChatModal.tsx:616`), with 80
(`IntentionEditSheet.tsx:155`) and 200 (`FirstActionCard.tsx:208`) in between, and
only `OnboardingReflectionActivity.tsx:96` renders a visible counter. A visible
counter is an extra string and arguably a counting surface, which sits awkwardly
beside "never counted". *Owner: Kyle, with D6's constraint in view.*

**D9 — What happens on a failed write, and what does it say?** §8 restricts coral to
genuine errors only. A save-failure line is a string nobody has written.
*Owner: Kyle.*

**D10 — Does the row need a distinct accessibility label?** Relevant because the
entry point is a compact row and the visible label may not be a sufficient
description on its own. *Owner: Kyle.*

**Settled already, so not on the decision list:** slice 8 needs **no** Insights-side
string — row 8 says it "feeds nothing until Insights ships", and Insights is
post-beta per §1 `:36`.

## 2.4 Ownership rule, for when the strings do exist

From `mobile/src/__tests__/copyDraftSentinel.test.ts:15-20`, which is the release
gate, not a convention:

> "Jen owns efficacy-adjacent and check-in copy; Kyle owns UI strings. ... which one
> applies is a property of the copy, not of who is available."

Applied to the D-list above, the likely split is **Jen: D1, D3, D4, D6** (and D7's
second-state string) — the naming, the prompt, and anything that frames what the
practice is for. **Kyle: D2, D5, D8, D9, D10** — structure, controls, limits, errors.
That split is a proposal, not a fact, and D1 in particular could go either way.

Mechanically: every drafted string added in slice 8 must carry a comment sentinel and
increment `EXPECTED_SENTINELS` in the same commit, naming the strings and the owner
in the commit message. The on-screen `[COPY GAP]` / `[Jen]` markers are retired; no
marker text may reach the UI.
